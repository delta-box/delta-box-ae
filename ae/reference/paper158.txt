δSandbox: Millisecond-Scale Checkpoint and Rollback
for Stateful AI Agents
Paper #158
Abstract
Emerging LLM-powered AI agent workloads, such as test-
time tree search and reinforcement learning, require high-
frequency state exploration, relying on rapid checkpoint
and rollback (C/R) of the complete sandbox state, including
files and process state. Existing mechanisms duplicate the
entire state, causing hundreds of milliseconds to seconds of
latency per C/R, which severely bottlenecks deep search and
large-scale fan-outs.
We observe that consecutive sandbox states between
checkpoints differ only marginally. Therefore, instead of full
duplication, a sandbox should only duplicate the changes
between consecutive checkpoints (Key Insight), yet the lack
of OS support makes this hard to realize. We propose a new
OS-level abstraction, δState, that delivers change-based C/R
for agents through co-designed OS mechanisms. First, δFS
checkpoints file state by freezing the writable layer and
inserting a new one, turning updates into copy-on-write and
rollback into a layer switch. Second, δCR quickly restores
process state by forking from a frozen template process.
A coordinator pairs the two so each checkpoint is one
consistent (filesystem, memory) state. Building on these
mechanisms, we present δSandbox, an agent sandbox with
millisecond-level C/R. On SWE-bench, δSandbox hides
its checkpoint work (10.83 ms) under inference and rolls
back in a mean 1.86 ms, with the same warm-template fork
driving low-cost RL rollout fan-out.
1 Introduction
LLM-powered agents now automate complex, multi-step
tasks, from code repair [1] to web navigation [2]. An agent
runs an iterative loop: it generates an action [3], executes it
in a sandbox [4], observes the outcome, and refines its next
step. To push capability further, agents increasingly scale
test-time compute [5] through tree search such as Monte
Carlo Tree Search (MCTS) [ 6] and Tree of Thoughts [ 7],
exploring multiple candidate paths, checking them against
execution feedback, and backtracking from failures.
In early text-based tasks (e.g., HotPotQA), backtracking
cost almost nothing: the agent simply truncated its prompt
history. A coding agent, by contrast, acts on real OS state [8,
9] through commands likerm,pip install, andsed. These
side effects persist on disk and cannot be undone by editing
history; reverting them requires checkpointing and restoring
the complete sandbox state. Because tree search backtracks
constantly, this expensive rollback lands repeatedly on the
critical path, creating a severe infrastructure bottleneck.
The sandbox state encompasses two tightly coupled
dimensions: durable filesystem state and ephemeral process
state. These dimensions must be captured and restored
jointly to prevent state divergence or context loss.
Test-time search stresses C/R along two axes at once: hori-
zontally, Best-of-N sampling spreads the inference budget
across many parallel trajectories, each needing a fast initial
clone [5, 10]; vertically, tree search such as MCTS backtracks
to arbitrary historical nodes, demanding fine-grained check-
point/restore of intermediate states.
Beyond test-time inference, reinforcement-learning (RL)
training of agent policies is a second pressure point [11–13].
Each training step must spin up 𝑘 independent sandboxes
from the same warm starting state, run them as rollouts,
and tear them down. Today’s approaches rebuild this warm
state per rollout with a fresh Docker container or a microVM
snapshot-restore, both in the hundreds-of-milliseconds to
seconds regime; with 𝑘 in the tens to low hundreds, fork
latency directly bounds training throughput.
Existing systems manage filesystem and process state sep-
arately, achieving C/R by duplicating the entire state into
a checkpoint image [14–18]. Full duplication is acceptable
for serverless cold starts [19–22], but prohibitively slow for
agents that checkpoint and roll back frequently on the critical
path. This creates three obstacles for agent workloads:
Challenge-1: Existing durable filesystem C/R is coarse-
grained and disruptive. A significant challenge is how to
efficiently checkpoint and restore the durable filesystem state
of an agent sandbox, including repository edits, installed
packages, caches, and temporary files. Naive file-level copy-
ing (e.g., copytree) scales with the directory size; Docker
commits scale with the mutated layer; and VM/block snap-
shots [18] operate at a coarse whole-VM granularity. These
approaches are tolerable for occasional resets, but too slow
for per-step rollback in MCTS or large fan-out in RL. Over-
layfs appears to be a natural alternative because each check-
point could demote the current writable upper into a read-
only lower and install a fresh upper, turning later writes
into copy-on-write. However, stock Linux overlayfs freezes
its layer stack at mount time: changing the stack requires
umount/mount, which is impossible while an agent keeps
files or working directories open and also flushes dentry/in-
ode caches [23]. Moreover, ordinary overlayfs copy-up can
duplicate an entire inherited file for a small edit, causing
file-size-proportional write amplification.
Challenge-2: Whole-state dump and materialization
limit process C/R efficiency. An agent’s process state

This model is acceptable for serverless cold-start systems

Challenge-3: Coupled sandbox state requires explicit
consistency management. Even if filesystem and process
C/R are optimized in isolation, agents cannot restore the two
dimensions independently. Process memory contains open
descriptors, mmap’d files, Python import caches, tool out-
puts, and assumptions about packages or tests on disk; the
filesystem records the edits and side effects that this memory
will continue to use after rollback. A naive composition of
overlayfs and CRIU can capture the two dimensions at differ-
ent logical times, register a partially completed checkpoint
after a failure, or resume a process before its target filesystem
is installed. Agent sandboxes therefore need explicit consis-
tency management for an atomic, failure-aware (filesystem,
process) state pair, not two unrelated snapshots.
This paper observes that consecutive checkpoints in agent
workloads differ only marginally, with only a few new files or
modified memory pages between steps. Therefore, instead of
duplicating the entire state, a sandbox should only duplicate
the changes between consecutive checkpoints (Key Insight).

on the next write. Finally, δFS uses XFS reflink under over-

2 Background and Motivation
2.1 Search and Exploration for AI Agents
Modern LLM-based agents increasingly rely on search and
exploration, whether tree-structured or parallel sampling, to
solve complex tasks such as math and code [1].
MCTS. MCTS is the tree-search paradigm, deciding through
selection, expansion, evaluation, and backpropagation [32,
33]; LATS [6] adapts it to LLM agents, using UCT-guided
selection to pick the most promising node and then gener-
ating and executing candidate actions in a sandbox. SWE-
Search [34] specializes this loop to SWE-bench code repair,
improving the success rate over single linear generation.
Best-of-N. BoN runs 𝑁 independent trajectories from the
same initial state and keeps the best by execution feedback [5,
10], i.e., 𝑁 clones of the initial environment.
RL training. RL post-training fans out rollouts (i.e., infer-
ence and agent exploration) at every training step. Chain-
based algorithms such as GRPO [12] launch 𝑁 independent
rollouts from the same initial state and score the completed
trajectories; tree-based variants such as Tree-GRPO [35] in-
stead branch additional rollouts from intermediate states of
existing trajectories, sharing the common prefix instead of
re-executing it. Either way the fan-out recurs at every train-
ing step, so sandbox cloning latency directly gates training
throughput; tree-based RL additionally requires forking from
arbitrary mid-trajectory states.
2.2 Agent Sandbox and Coupled Checkpoint/Restore
To support efficient state exploration, AI agents rely heavily
on two critical primitives: checkpoint and rollback. Sandbox
runtimes [18, 20] typically provide these primitives for iso-
lated execution environments, allowing agents to execute
code, capture milestone snapshots, and safely revert state
after failures. RL fan-out (§2.1) uses the same mechanism: the
runtime checkpoints one warm environment and restores it
𝑁 times, once for each rollout.
While most modern agent frameworks utilize some form
of checkpoint and rollback, their implementations are of-
ten inefficient or incomplete. E.g., frameworks like SWE-
agent [36] and OpenHands [37] perform model reasoning on
the host and cheaply reset the in-sandbox repository using
git worktree. However, this approach fails to checkpoint
the running process, leading to a loss of the execution context
(e.g., debugging history). To preserve this context, current
frameworks interact with the environment via a persistent
daemon process inside the sandbox (e.g., E2B’s envd [ 4]).
In this setup, a rollback only undoes file edits, leaving the
process state desynchronized. Recovering the true process
state requires replaying every prior action from the initial
state, which is a latency-heavy operation proportional to the
search depth and may severely bottleneck the critical path
of backtracking search.
Coupled C/R matters. The state of a sandbox spans two
interdependent dimensions: the filesystem (FS) (working di-
rectories, installed packages) and the process memory (ex-
ecution context, open file descriptors). A partial rollback
inevitably desynchronizes them. If only the FS is rolled back,
the still-live process retains memory of file contents that
no longer exist on disk. Conversely, if only the process is
rolled back, its restored memory operates on files that have
been mutated beyond its expected state. Either mismatch
breaks the strict consistency required for correct tree search,
necessitating a truly coupled checkpoint/restore mechanism.

2.4 Insight: Delta-Based Checkpoint and Restore
To understand the actual state mutation behavior of real-
world agents, we analyzed the state changes during SWE-
Search MCTS trajectories. As shown in Fig. 2, we observe
that during each interaction step, an agent modifies only a
minuscule fraction of the total sandbox state. Specifically,
the per-step deltas of the process memory and the filesystem
constitute on average only 12.2% and ∼0.005% of the total
state, respectively (Fig.2(a)). Furthermore, this highly local-
ized mutation pattern remains consistent across different
interaction rounds and workload scenarios.
This observation leads to our core idea: rather than dupli-
cating the entire container state, an efficient agent sandbox
should only capture and restore the state deltas between consec-
utive checkpoints (Key Insight). By focusing exclusively on
the incremental changes, across both process memory and
filesystem dimensions, a sandbox can bypass the massive I/O
and memory copy overheads of full-system C/R, enabling
the millisecond-scale state management required for modern
agentic search.
3 Overview
Based on the insight, we present δSandbox, a new agent
sandbox realizing millisecond-scale C/R.
3.1 System Architecture
δSandbox extends existing sandboxes (e.g., microVMs) with
two key components: δFS and δCR.
δFS: Delta-based filesystem. A fundamental challenge for
δSandbox is achieving highly efficient checkpoint and restore
for filesystem states. A natural approach to this problem is
applying copy-on-write (CoW) techniques, widely used in
memory management (e.g., fork()), to the filesystem. By
treating existing files as read-only and triggering copies only
upon modification, a system could theoretically record just
the state diffs between checkpoints.
Overlayfs [23] offers the closest realization of this idea. It
provisions a writable upper layer for apps while maintaining
a read-only lower layer that encapsulates the base sandbox
image. However, overlayfs suffers from a critical limitation:
its layer stack is fixed and static at mount time. Altering the
layers during runtime requires a complete umount/mount
cycle, which flushes caches and breaks active file descriptors,
making it infeasible for running agent processes.
To resolve this, we introduce δFS, a new file system ex-
tending overlayFS that supports dynamic, runtime overlay
reconfiguration. When an agent completes a task step and
requests a checkpoint, δFS does not duplicate the underly-
ing files. Instead, it dynamically freezes the current writable
layer into a read-only state and seamlessly inserts a new
writable upper layer on top of it. Consequently, all subse-
quent file updates trigger copy-on-write to this new upper
layer. Through this mechanism, a checkpoint operation is
reduced to a lightweight layer-insertion, and a rollback be-
comes a simple layer-removal, perfectly aligning with our
diff-based C/R insight. δFS further uses reflink-enabled XFS,

δCR: Delta-based process checkpoint/restore. Process-
level state management has seen extensive prior research.
Methods like CRIU [ 16] and fork() [20, 40] are widely
used. However, applying them directly to agent workloads
presents severe challenges. While recent efforts have opti-
mized CRIU’s restore latency, its checkpoint latency, even
using incremental dumps [41], remains 100—1,000 ms. While
fork() offers milliseconds cloning, it introduces its own limi-
tations: (1) it requires the parent process (template) to remain
resident in memory, scaling poorly for agent exploration;
(2) synchronous CoW page faults scatter latency across the
agent’s critical path post-restore; and (3) both CRIU and
fork() are only safe if the process holds no long-lived ex-
ternal state. Standard Python LLM SDKs (e.g., OpenAI) vio-
late this safety requirement by spawning persistent HTTP/2
connection-pool threads in the background, which fatally
deadlock upon a template fork.
To this end, δSandbox introduces δCR, a hybrid process
C/R mechanism that synthesizes the durability of CRIU
with the speed of fork(). During a checkpoint, δCR si-
multaneously executes an asynchronous CRIU incremental
dump and a template-creating fork(), seamlessly hiding
both operations within the LLM I/O window. During a re-
store, δSandbox prioritizes the fast-path by forking the resi-
dent template. To bound memory costs, δCR employs a tem-
plate pool, transparently falling back to CRIU’s lazy-pages
restore if the template has been evicted. δCR introduces an
asynchronous pre-warming mechanism to eliminate runtime
CoW faults from the critical path, alongside a Network Proxy
Daemon that isolates persistent I/O connections outside the
agent process, guaranteeing that the templated processes
remain perfectly forkable.
Coordination and optimizations. To ensure atomic,
coupled state transitions, δSandbox employs a two-tiered
StateManager to orchestrate δFS and δCR, maintaining
each checkpoint as one δState: a consistent, transactional
(filesystem, memory) pair. The global Sandbox Controller
runs on the host, maintaining a snapshot index tree
isomorphic to the search tree, where each node records
its CRIU dump path and overlay layer-stack configuration.
Simultaneously, the Guest Daemon executes the local C/R
sequences inside the VM, keeping state management off the
host’s critical path (§5).
δSandbox also introduces agent-specific optimizations to
further minimize overhead. First, a semantic-aware light-
weight skip mechanism avoids unnecessary snapshots. Sec-
ond, δSandbox utilizes a reachability-aware garbage collector,
to reclaim unused checkpoints.
3.2 System Workflow
Fig. 3 shows the overall workflow of δSandbox. δSandbox
efficiently supports two critical workloads: millisecond-scale
rollback to a prior node for tree search, and rapid 𝑁 -way
fork-out from a frozen template for parallel RL training.
3.2.1 Coupled δCheckpoint and δRestore. We intro-
duce the workflow of two primitives.
δCheckpoint. A checkpoint operation is orchestrated by
the StateManager and executed entirely off the host’s critical
path by the Guest Daemon inside the sandbox. First, the dae-
mon captures the process state via δCR: the agent executes a
fork() at a quiescent point to create a frozen template, while
a CRIU incremental dump is asynchronously submitted. Con-
currently, the daemon triggers the δFSioctl to freeze the
current FS upper layer and install a fresh writable layer. The
agent remains perfectly quiescent across both operations.
This guarantees that every δCheckpoint registers a strictly
consistent (FS, memory) state delta. Because this entire se-
quence executes concurrently while the agent awaits its LLM
response, the checkpoint cost is completely hidden behind
inference latency.
δRestore. A restore operation seamlessly reverses this pro-
cess. When rollback, the Sandbox Controller instructs the
Guest Daemon to discard the current active agent. The dae-
mon then uses the δFSioctl to dynamically revert the FS

4 Detailed Design
4.1 δFS: Dynamic Overlay Filesystem
Overlayfs fixes its layer stack at mount time. As shown in
Fig. 4, δFS releases this restriction and supports dynamic
layers.
Interface. To expose this dynamic capability,δFS introduces
ahotswitch ioctl, allowing the controller to reconfigure the
overlay layer stack in place. The ioctl accepts a {mount,
option, style} configuration, which explicitly defines the
target state: a writable upper layer, its associated workdir,
and an ordered chain of read-only lower layers.
During a checkpoint, if the current upper is dirty, the State-
Manager uses this interface to sink it into a frozen lower
layer and install a new writable upper layer above it. Con-
sequently, files in the prior layer remain reachable, but any
subsequent modifications trigger a copy-on-write to the new
upper layer, successfully isolating the state delta. The restore
path is even simpler: the StateManager invokes the ioctl to
specify the exact lower layer chain of the target checkpoint
and installs a fresh writable upper layer above it. Because
this process is purely a layer reconfiguration, it operates
with 𝑂 (1) efficiency regardless of how far back in the search
tree the target checkpoint lies. The ioctl is entirely synchro-
nous; once it returns, subsequent path resolution observes
the new stack; already-open descriptors are handled by the
lazy rebinding mechanism below.
Layer lifetime. A hot-switch completes without freezing
the filesystem, so open files and in-flight lookups may still
reference the old layer stack after the ioctl returns.δFS there-
fore reference-counts each retired stack: a cached overlay
entry holds a reference to the stack it was resolved against,
and the kernel frees a retired stack only after its last reference
drops and an RCU grace period has elapsed.
Open files across checkpoint and restore. Files opened
prior to a checkpoint present a challenge: their FDs may
point to backing files within an outdated layer stack. δFS
resolves this via a generation-based lazy rebinding mecha-
nism. Each inode caches the checkpoint_gen at which it
was last resolved. During any file access, the kernel compares
this cached generation against the current global filesystem
generation. If the generations match, the access proceeds di-
rectly via the fast path with near-zero overhead. If they differ,
the kernel re-resolves the inode against the new layer stack:
read-side accesses only refresh stale references and keep
reading from read-only layers, while write-side accesses first
detach the descriptor from its stale backing and redirect it to
the current writable upper, copying file data when needed.
Both paths update the inode’s generation and backing under
a per-inode mutex. Furthermore, if concurrent threads race
to copy up the same file, the loser simply reuses the already-
created upper layer rather than retaining its stale backing
file.
Descriptor semantics. A rollback replaces the filesystem
view underneath live file descriptors. δFS makes this deter-
ministic. After a checkpoint, writing through a stale descrip-
tor copies up from its frozen backing into the current upper,
so checkpointed history remains immutable. After a restore,
a descriptor whose path exists in the target state rebinds
reads and later copy-ups to that state. If the file existed only
in a discarded upper, the descriptor continues through an
anonymous backing copy and never resurrects the old path.
XFS reflink. δFS can run over different backing FSes, but
δSandbox uses reflink-enabled XFS to bound write ampli-
fication. For regular-file data copy-up, overlayfs first tries
vfs_clone_file_range; on XFS this clones extents by ref-
erence, so the copied-up file shares physical blocks with
its source until those blocks are overwritten. Reflink shar-
ing composes across generations: an extent left unmodified
across 𝑁 checkpoints occupies one physical block.

4.2 δCR: Diff-based Checkpoint/Restore
δCR manages the process (memory) dimension of each check-
point around two paths: a warm-template fast path, which
checkpoints by forking off a frozen template and restores by
forking it back in low milliseconds, and a durable CRIU [16]
fallback, with incremental dumps via soft-dirty page tracking
and lazy-pages restores via userfaultfd [42]. Fig.5 summa-
rizes its three components, the template pool (§4.2.1), the
async-warm thread, and the network proxy (§4.2.3), together
with the two restore paths.
4.2.1 Template Pool and Fork-Based Restore. The fast-
path restore mechanism relies on a template pool , which
maintains a registry of frozen (SIGSTOP’d) processes, each
keyed to a specific snapshot ID.
Checkpoint flow. During checkpoint 𝑘, the Guest Daemon
issues a fork request to the agent’s control FIFO; the agent
forks at its next quiescent point (i.e., no syscalls in flight, no
files half-written). The frozen child registers astemplate_k in
the pool while the active worker continues in the main loop.
A short-lived fork helper re-parents the template away from
the active process. δCR then takes an incremental dump in
the background as a durable fallback for crash recovery and
cold-path restores.
Inference-masked checkpointing. Because a checkpoint
runs while the agent awaits its LLM response, both the dump
and the fork are hidden inside the inference window. The
one obstacle is the agent’s live LLM connection;δSandbox
offloads it to the network proxy (§4.2.3) so the request keeps
progressing while the agent forks and the dump completes.
The agent’s brief checkpoint pause (∼11 ms in δSandbox) fits
comfortably within the LLM inference latency.
Fast-path restore (template hit). To restore checkpoint 𝑘
while template_k is alive, the Guest Daemon kills the current
agent, reverts the layer stack, and forkstemplate_k; the child
resumes via SIGCONT from the instruction right after the
original checkpoint, with the filesystem already switched to
match. The fork duplicates only page tables, so restore com-
pletes in low milliseconds; an optional async-warm thread
absorbs the post-fork CoW faults off the critical path. The
C/R protocol makes the worker single-threaded at the mo-
ment it forks: the fork happens only at a quiescent point,
after transient thread pools are shut down, and long-lived
network threads live in the separate proxy process (§4.2.3).
Inherently multi-threaded runtimes can be supported by
adopting existing techniques from prior systems [20].
Slow-path restore (template miss). If template_k has been
evicted, δCR falls back to CRIU lazy-pages restore. CRIU
reconstructs the process skeleton, registers all anonymous
VMAs with userfaultfd, and resumes the process, faulting
in pages on demand from the dump images. To minimize
critical-path latency, the background async-warm thread
prefetches hot-zone pages off the critical path.
𝑁 -way fork-out ( fork_n). RL fan-out (§3.2.2) reuses the
template-fork protocol through a batching primitive that we
implement in δSandbox: fork_n wakes the frozen template
once, forks all 𝑁 children in one cycle, and re-suspends it,
eliminating 𝑁 −1 per-child resume/suspend round-trips com-
pared with issuing 𝑁 one-at-a-time template restores. FS
isolation is per child: the source’s overlay layers are frozen
once at the branch point (one δFS ioctl), and each child re-
ceives its own overlay mount whose read-only lowers are the
frozen chain and whose writable upper is private, so isolating
a child costs one mount and no data copy. These mounts are
pre-created before the fork, so every child resumes directly
into a ready, private filesystem view.
4.2.2 Bounding Memory under Deep Search. By de-
fault δCR writes each CRIU dump to an image file on the
FS, kept in the page cache for fast cold-path restore but
reclaimable under memory pressure; a checkpoint’s unre-
claimable resident cost is therefore just its frozen template
(CoW page tables and privatised pages). Resident memory
therefore tracks the live template pool, which grows as the
MCTS tree deepens; left unbounded it would accumulate
until the guest exhausts memory. δSandbox bounds it along
three complementary axes: it avoids creating snapshots for
cheap-to-recompute nodes, caps the resident template set,
and reclaims snapshots the search can no longer reach.
Skipping read-only nodes. Many agent actions, such as
grep, cat, and find, are read-only and idempotent: they
leave the filesystem untouched and produce no agent state
that a restore must reproduce. A semantic classifier inspects
each action and, for such a node, skips both the CRIU dump
and the layer switch, recording only a metadata marker (par-
ent snapshot ID and action). A restore to that node simply

memory regardless of how large the search tree grows.
Reachability-aware garbage collection. A recency- or
visit-count policy is unsafe for MCTS: discarding a node
UCT may still select, or an ancestor whose delta image a
reachable node’s incremental dump chains back to, triggers a
restore-fail re-selection loop that wastes the iteration budget.
δSandbox instead drives GC from a persistent node-to-image
index, in which each node records its parent, children, and
delta-image ID. A pass marks the reachable set and reclaims
the rest at leaf or whole-subtree granularity. A delta image is
freed only when its node is unreachableand no reachable de-
scendant or shared node depends on it, so reclamation never
breaks the–prev-images-dirchain. Since an unreachable
node is never re-selected, GC drops both its frozen template
and, when on-disk image storage is scarce, its delta image. GC
runs asynchronously, off the checkpoint critical path. Fig.6a
shows the combined effect: with no policy, resident memory
climbs with tree depth; lightweight-skip and reachability-
GC keep it flat. Lightweight-skip additionally diverts most
read-only nodes to a near-free metadata write (Fig.6b).
Async-warm. After a fork, the child shares all pages with
the template copy-on-write, so its first write to each page
takes a synchronous CoW fault. An async-warm thread
in the Guest Daemon (keeping the agent single-threaded)
absorbs these faults off the critical path: right after the
fork it walks the child’s anonymous writable VMAs via
/proc/[pid]/mem, forcing each page’s private copy in the
background while the child runs. The latency win is not
free: privatising every page destroys CoW sharing with the
template (over 5× resident inflation, Fig.6a) and marks every
touched page soft-dirty, degrading the next incremental
dump to a full one. δSandbox therefore disables async-warm
by default, enabling it only when post-restore fault latency,
rather than memory, is the bottleneck.
4.2.3 Reusable I/O during Checkpoint with a Network
Proxy. Fork-based restore is safe only if the frozen tem-
plate’s address space holds no long-lived external state, such
as live network threads. However, standard LLM SDKs in
Python (e.g.,openai oranthropic) violate this requirement
by spawning background HTTP/2 connection pools and
ThreadPoolExecutor workers. Forking a template contain-
ing these threads leads to fatal issues: keep-alive TCP sockets
survive as half-open file descriptors, connection-pool states
diverge, and threads frozen mid-handshake permanently
deadlock the frozen template.
δSandbox resolves this with a network proxy daemon , a
separate process in the same sandbox that owns all LLM
clients and connections. The agent never links the SDKs;
it exchanges small FIFO tokens (each ≤PIPE_BUF, hence
atomic) with the proxy over a shared directory, keeping ev-
ery socket and SDK thread out of its address space. Being a
separate process, the proxy is excluded from both the CRIU
dump and the template fork, so a template carries only the
agent’s own short-lived threads. During a checkpoint the
agent pauses only to inline-fork; the in-flight LLM request
keeps progressing inside the proxy, which buffers the re-
sponse until the agent resumes. After a fork-based restore
the child inherits the FIFO descriptors from the template,
resuming communication with no reconnection protocol.
δSandbox does not currently support network I/O rollback,
which may incur external side effects.
4.3 StateManager Coupling Protocol
StateManager coordinates the system to enforce an invariant:
every saved state is a consistent (filesystem, memory) pair .
Consistency protocol. During a checkpoint, consistency
rests on a quiescence invariant: the worker replies only af-
ter finishing its action and returning to a single-threaded
control point, where it blocks on its control FIFO until the
next command. The fork (memory) and the δFS ioctl (filesys-
tem) therefore observe the same post-action state, and the
asynchronous dump serializes the corresponding quiescent
process state. During a restore, the restored child blocks at
the same control point, and the StateManager issues it com-
mands only after both the layer switch and the fork have
completed, so the agent never executes against mismatched
files.
Failure atomicity and concurrency. δSandbox is failure-
atomic at the level of checkpoint visibility: a checkpoint
becomes restore-visible only at its final registration step, so

a crash mid-sequence leaves the partial checkpoint unrefer-
enced, and registered checkpoints keep their frozen layers,
which are immutable. A slow-path restore that needs the
CRIU image waits for any in-flight dump to complete; the
fast path reads only the frozen template. On restore, the tem-
plate fork proceeds concurrently with the layer switch (the
two touch disjoint kernel state); the synchronization point
is the next-command boundary above, not the fork itself.
Value-time test isolation. Evaluating a node often runs
tests (e.g., SWE-Search [ 34]), whose side effects such as
__pycache__, pytest caches, and temporary files would per-
manently pollute a stateful, in-process worker; stateless sand-
boxes avoid this only by discarding the sandbox. δSandbox
instead uses its own millisecond C/R primitive as a transac-
tion bracket: the StateManager checkpoints before the test,
restores once the result is collected, and then records the re-
sult as the node’s observation and reward. This is only practi-
cal because δSandbox makes coupled C/R a millisecond-scale
primitive rather than a second-scale sandbox operation.
5 Implementation and Deployment
δSandbox is deployed inside Firecracker [ 18] microVMs;
the design is not Firecracker-specific and carries over to
container- or other VM-based sandboxes. δFS adds ∼1.8K
LOC of C to overlayfs; it builds as a loadable kernel module
against stock Linux 6.8. δCR is ∼3.8K LOC of Python orches-
trating CRIU, the template pool, the async-warm thread, and
the network proxy (§ 4.2). The fork-out path (§ 4.2.1) is a
separate ∼330-LOC module that adds the batched fork_n
op to the template pool’s control-FIFO protocol. CRIU dump
images and overlay uppers both reside on the XFS rootfs,
where reflink CoW is block-granular; recent dump images
stay in the page cache for fast restore and are reclaimed
under memory pressure.
Deployment model. The StateManager’s two tiers (§3) map
onto a Host–Guest split: the host-side Sandbox Controller
manages VM lifecycle and workload provisioning, while
the in-VM Guest Daemon owns the entire per-event C/R
sequence, keeping all latency-sensitive work in a closed loop
inside the guest; the KVM host is unmodified. Because C/R is
process-level, a single VM can host multiple independently
checkpointable agents that share one kernel and the read-
only base layers; rolling back one search branch leaves the
others untouched, which a VM-level snapshot cannot do (it
captures all processes at once).
Framework integration. δSandbox complements
application-level frameworks such as LangGraph [43] and
LangChain [44], whose checkpoints capture logical state
only and cannot undo OS-level side effects. Integration can
be transparent, pairing the framework’s state save/restore
events (e.g., a LangGraph checkpoint saver) with coupled
OS-level C/R, or explicit, exposing sandbox_checkpoint/
sandbox_restore tool nodes so the agent or search strategy
controls physical rollback directly.

6.1 Experimental Setup
Hardware. All experiments run on a four-socket server (96

and snapshot images placed on an NVMe SSD. RL training

use δSandbox’s default configuration: each checkpoint takes

Workloads. We draw four MCTS-trajectory archetypes

6.3.3 Correctness. An integration suite drives the δFS
ioctl directly; its 53 checks cover checkpoint semantics across
generations, open handles (stale and deleted-but-open de-
scriptors, advisory locks), cache and mmap coherency, and
data integrity over reflink, all passing with a clean kernel

chains stay valid up to overlayfs’s 500-layer cap. Finally, the
replays of §6.2 double as an end-to-end consistency check:

back, so any divergence between restored filesystem and
memory breaks the replay; all replays completed with zero
mismatches.
7 Related Work
Agent sandboxes. Recent agent sandboxes [4, 14, 15, 48]
primarily optimize isolation and startup latency, but
provide only coarse-grained rollback. Daytona’s OCI
workspaces [ 14] use Docker-layer commits and do not
capture live process state. E2B [ 4] uses Firecracker mi-
croVMs and pre-warmed templates, improving isolation
but retaining VM-granularity snapshot costs. ZeroBoot [48]
pushes VM cloning further with KVM-level CoW memory,
but each branch remains an entire VM, with a shared
block device, kernel-level dirty state, and no independent
rollback for multiple in-VM trajectories. Yan’s fault-tolerant
sandbox [15] moves toward transactional agent execution,
but its filesystem rollback based on tool interception and
userspace CoW simulation yields second-scale checkpoints
and no coupled memory snapshot.
A position paper [49] frames agentic exploration as a sys-
tems problem and, like δSandbox, identifies fast forking and
fork-aware state management as foundational gaps; it re-
mains a diagnostic framing, whereas δSandbox contributes
a concrete millisecond-scale OS mechanism.
Concurrent work Crab [50] tackles the same gap from a
different angle. Crab proposes a semantics-aware approach
using an eBPF-based inspector to determine checkpoint gran-
ularities. In contrast, δSandbox focuses on optimizing the
full OS-level checkpoint/restore mechanism itself to achieve
millisecond latency. The two approaches are complementary.
Sandboxes for serverless computing. Serverless systems
have long optimized sandbox reuse, cold start, and snap-
shot restore, but their unit of reuse is a function invocation
rather than a rollback point inside a long-lived agent tra-
jectory. TrEnv-X [38] repurposes sandboxes across invoca-
tions using OS-level memory templates backed by CXL or
RDMA memory pools, while earlier cold-start systems ac-
celerate process creation, language runtime initialization,
or post-restore fault handling for short-lived functions [19–
21, 39, 51, 52]; Spice [52] moves restore-path fault resolution
into the kernel with Overlay VMAs. They are orthogonal
to δSandbox. A serverless instance typically restores a com-
pute image and then runs one request, whereas δSandbox
repeatedly descends and backtracks within one task.
Checkpointing optimizations. Existing checkpointing
systems [53–58] provide important building blocks, but none
provide the coupled, fine-grained rollback interface needed
by stateful agents. CRIU [ 16] (which δCR builds on) and
DMTCP [59] do process-level checkpoint/restore but not
the coupled, high-frequency rollback agents require. Fire-
cracker [18] and Sabre [60] restore whole VMs, too coarse
for branches isolated inside one VM. Btrfs [61] and ZFS [62]
snapshots give block-level CoW but need a separate storage
stack, and EROFS [63] offers read-only overlay layers with-
out a writable upperdir; δFS instead hot-switches overlayfs
layers over XFS reflinks. LangGraph [43] and LangChain [44]
checkpoint only logical agent state, which cannot undo exe-
cuted commands’ OS-level effects.
8 Conclusion
We present δSandbox, an OS-level rollbackable sandbox de-
signed to accelerate agent workloads such as test-time tree
search and reinforcement learning. Recognizing that sub-
sequent agent states are highly similar, δSandbox eschews
full state duplication in favor of diff-based checkpoint and
restore. To achieve this, δFS enables dynamic, unmount-free
overlayfs layer switching for filesystem C/R, while δCR uti-
lizes CRIU dumps and warm-template forking for memory
C/R.
